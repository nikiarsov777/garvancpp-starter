Jobs

Jobs são unidades de trabalho em segundo plano. Cada job é uma classe C++ que herda de Garvan::Job. Podem ser acionados diretamente, a partir de um event listener ou via a admin HTTP API (que é o que kalpasan job:dispatch faz internamente).

Job API

Sobrescreva quatro coisas e forneça uma factory estática:

// app/jobs/MyJob.h
#include "queue/Job.h"
#include "tools/JsonValue.h"

namespace AppJobs {

class MyJob : public Garvan::Job
{
public:
    MyJob() = default;
    MyJob(std::string arg) : arg_(std::move(arg)) {}

    void handle() override;                                 // faz o trabalho
    std::string jobName() const override { return "MyJob"; }
    std::string connection() const override { return "sync"; } // sync | async | database

    Garvan::JsonValue payload() const override;             // serializa para filas persistentes
    static std::unique_ptr<Garvan::Job>
        fromPayload(const Garvan::JsonValue& p);            // inverso de payload()

private:
    std::string arg_;
};

} // namespace AppJobs

Registar um job

Registe cada user job em JobServiceProvider::register_(). Use JobRegistry::bind() diretamente com o nome curto de jobName():

// app/providers/JobServiceProvider.cpp
Garvan::JobRegistry::bind("MyJob", &AppJobs::MyJob::fromPayload);
Não use GARVAN_REGISTER_JOB para user jobs

A macro GARVAN_REGISTER_JOB(AppJobs::MyJob) stringifica o token inteiro e regista a chave como "AppJobs::MyJob", que depois não corresponde ao jobName() nem ao nome curto que kalpasan job:dispatch espera. Ver a correção em app/providers/JobServiceProvider.cpp:18.

Dispatch

De qualquer lugar do código — controller, listener ou outro job:

#include "queue/JobDispatcher.h"
#include "app/jobs/MyJob.h"

Garvan::JobDispatcher::dispatch(std::make_unique<AppJobs::MyJob>("hello"));

O dispatcher encaminha o job para o driver nomeado por job->connection(). Os drivers são ligados por service providers; hoje apenas "sync" está ligado no starter.

SyncDriver

SyncDriver executa o job inline no thread que chama. Este é o default em Phase A e dá a mesma semântica de chamada-e-retorno que uma função normal — perfeito para testes, tarefas de baixo throughput ou pipelines disparados por um pedido HTTP. Drivers async e baseados em base de dados encaixarão na mesma API do JobDispatcher em fases posteriores sem alterações nas suas classes de job.

Exemplo: SendTestMail

O AppJobs::SendTestMail incluído (app/jobs/SendTestMail.h:21) é um job real e enviável. O seu handle() abre uma sessão SMTP com libcurl, envia um email HTML usando o bloco MAIL_* de .env e regista o resultado em stdout. Ver Mail (SMTP) para a parte SMTP e Kalpasan CLI para o verb job:dispatch.
